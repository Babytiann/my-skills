# 从方案到 UI 改动评审 HTML：示例调研

调研日期：2026-09-28。目标是让方案作者交付一份能在浏览器中查看的 UI 改动评审稿，帮助读者判断改哪里、改完什么样、什么条件下会变化。

本次已确定的使用方式：只能点名调用；默认交付评审页与关键交互；默认在本机浏览器预览。调研结果用于编写 `plan-ui-preview`，不修改已有规划或写作 skill。

## 设计稿为什么便于评审

### 先给所在环境，再放大改动

v6 先画会话窗口，让读者看清气泡、输入框与队头的关系，再依次展开 hover 的落点、五类原子、局部细节、文件浮窗和批注浮窗。v3 先画附件栏与菜单的组合效果，再展示 `/`、`@` 默认、`@` 搜索、`$`、空结果、输入框和气泡。

这种阅读顺序解决两个问题：先知道改动放在哪里，再检查局部是否符合规则。只有一处小改动时，不必为凑结构重画完整产品。

### 同一种形态少画，条件变化说清楚

示例把 A/B/C 等标记放在具体位置，旁注用同一个字母定位，并说明“什么条件 → 发生什么变化”。例如：标签过长时省略，命令名不向参数让位，行末放不下整颗 chip 时整体换行。

同一布局中的长短内容、权限差异或开关状态，可以用标注或局部切换说明。浮窗、展开编辑态等形态明显不同的情况，再增加独立画面。主题切换也是复用同一画面的一种方式，但不意味着每个项目都必须做明暗两套。

### 画面里的数据参与解释规则

示例使用长文件名、长参数、多条批注、多张不同宽高比的图片和长消息，让省略、折行、滚动及只读差异真实出现。演示数据应触发本次方案关心的条件，而不是用一组永远不会溢出的短文本掩盖问题。

### 产品画面与评审说明分开

界面承担用户操作，旁注承担解释。架构术语、实现范围、争议和模拟边界不应变成产品内部文案。不能为了展示协议重构，额外画出方案没有要求的管理面板。

## 方案如何落到画面与交互

| 方案要求 | 需要表达的 UI | 需要检查的差异 | 来源 |
| --- | --- | --- | --- |
| 输入框与气泡读取同一份对象内容 | 同一段文字与文件、技能、命令、引用、图片的混排 | 发送前后顺序与身份保持一致 | 方案第 3、8 节；v6 全貌和细节 |
| 评论集中到 carry 队头 | 一批评论对应一个 pill，正文无评论副本 | 待发送可操作，历史气泡只读；仅有评论也能发送 | 方案第 8、9 节；PR 3、8 |
| hover 与全文阅读 | 输入框和气泡中的浮层落点、文件及批注浮窗 | 对象所在位置、手势、权限决定行为，不能给所有 chip 统一绑同一个动作 | 方案第 7、8 节；PR 8；v6 |
| carry 的来源和生命周期 | 队头与正文分离，必要时演示发送结果 | chip 删除后的关联变化，发送成功清除非 ambient 项，失败保留 | 方案第 5、8 节 |
| 菜单样式与检索呈现 | 分组、来源、选中项、默认列表、搜索结果与空结果 | 长名称和描述如何分配宽度，空结果如何收缩 | PR 2、5、9；v3 |
| 附件栏与正文联动 | carry → 附件栏 → 正文，正方形缩略图 | 点附件 X 同时删除对应 chip；仅删 chip 时图片仍在 | PR 9；v3 |
| 内容超过可见区域 | 附件折行、正文独立滚动、长气泡展开 | 附件不横滚，carry 和附件栏不随正文滚动 | PR 9；v3、v6 |

Definition 注册、五支 parts、handler 补全、消息落库、目录初始化属于支撑机制。它们可能改变可见结果，但本身不等于新页面。对纯后端且没有 UI 影响的方案，说明不需要 UI 评审稿即可。

实际生成前，普通清单已经足以建立对应关系：

| 来源要求 | 页面或区域 | 触发条件 | 结果状态 |
| --- | --- | --- | --- |
| PR 9：删除附件时联删正文胶囊 | 附件栏与正文 | 点击某张图片的 X | 该图片及全部对应 chip 消失，其他内容保留 |
| PR 9：删除胶囊不删附件 | 正文 | 删除一枚图片 chip | 该 chip 消失，附件栏图片保留 |

生成后可在清单中补充 HTML 锚点或区域名称与验证结果；不需要另建 manifest、专用 JSON schema 或页面生成器。

## 视觉与 HTML 实现观察

- 两份示例用中性底色、弱边界、有限强调色承载信息。chip 的颜色区分对象类型，不是给每块容器套不同主题色。
- 示例包含容器和较强字重，并非所有细节都应照搬。用户对新稿的要求是细线条标题、克制颜色、避免 card 套 card；目标项目的现有组件和规范仍是视觉依据。
- 两份成果都是直接返回的 HTML，内联 CSS 与 JavaScript，无需启动前端构建流程。部分画面由内联 JavaScript 填入 DOM，不能据此声称关闭 JavaScript 后仍完整可读，也不应把某种 DOM 生成方式写成通用要求。
- 图标和部分演示缩略图使用内联 SVG 或 data URL。新稿应优先使用实际提供的素材；用示意素材时说明其性质，不能假称它来自现有产品。
- 两份 HTML 均引用 Google Fonts，并带系统字体回退。浏览器访问过程中出现过加载超时，之后能够显示；本次没有确认超时原因。新稿应避免关键内容必须等待外部字体或其他不稳定资源才能出现。

默认单文件 HTML 是降低预览成本的手段。已有大量实际素材时允许附带资源目录，不必为了单文件强行嵌入所有资源或重画素材。

## 展示出来，不等于交互已经实现

| 项目 | 本次证据 | 对新 skill 的启示 |
| --- | --- | --- |
| v6 长消息展开 | 浏览器点击后从“查看消息”变为“收起”，完整内容展开 | 可以实际操作验证，交付时明确列为已验证 |
| v3 菜单选中条、两份稿子的主题切换 | 源码包含事件处理与样式切换 | 有实现依据；要声称浏览器验收通过，还需实际操作 |
| v6 批注原文展开、浮窗滚动 | 源码包含展开与滚动逻辑 | 只覆盖相应局部能力，不代表批注业务已接通 |
| v3 附件 X | 展示元素，无删除事件；联动规则写在旁注 | 原稿只说明效果，不能声称已验证删除联动 |
| v6 部分文件浮窗按钮 | 使用展示性的 span，浮窗预先展开 | 画出了浮窗，不能推断打开、关闭和模式切换都可操作 |

新 skill 只需实现帮助判断本次方案的关键交互。例如专门评审附件删除联动时，两种删除结果必须能操作；与当前改动无关的模型选择等控件可以仅展示。已实现、已操作验证、仅展示这几种状态应如实区分。

## 来源冲突与范围边界

这些问题属于本次 Composer 案例，作为处理冲突的例子，不固化成其他产品的业务规则。

1. **菜单的发送动作。** 主方案写到无必填参数时 Enter 直接发送；PR 4 按 execution 分流，send 写入命令文本，无必填参数的 control 才当场执行。需要先确认本次生成针对哪个范围，不能混成一个未被确认的行为。
2. **裸 `/workflow`。** 正文要求空参拒发，评论提出允许结合上下文裸调用。讨论没有明确收敛为空参规则变更，不能把评论自动当作对正文的覆盖。
3. **手势表述。** 主方案把单击定位与双击阅读分开，v6 部分说明写“点文件原子”打开阅读浮窗。生成实际交互时需要确认目标规则，不能靠样稿措辞猜测单双击。
4. **阶段与编号。** PR 表格中 8、9 的前置为 PR 7，正文仍写 PR 6；PR 3 的 carry 接入编号也有陈旧引用。PR 3 的中间态明确先用已有队头形态，整份最终方案与单 PR 稿不能混用。
5. **版本与评论范围。** 部分正文提到 v3，而读取到的设计方案标题为 v2。用来源、revision 和具体段落定位，不仅凭标题数字判断新旧。评论池侧栏与新会话入口另有责任范围，删除 Composer 评论 chip 不等于删除侧栏复制入口。

来源有冲突时，保留出处与差异；只追问会改变关键画面或操作的缺口，继续制作不依赖答案的部分。无依据的旧界面不能补成“改前图”；缺基线但可以形成有用方案时，明确标注为示意。

## 沉淀到 skill 的交付标准

输入是已有方案和可获得的视觉依据。输出是带必要评审说明的 HTML、用户可打开的预览入口，以及实际验证与仅展示部分的简短说明。

完成需要同时满足：

1. 本次范围内的 UI 改动都有对应画面、可触发状态或明确标注的待确认项。
2. 已用浏览器看到实际内容，并操作检查关键交互；对未解决的错误或资源缺失如实说明。
3. 用户能打开同一份文件或预览地址。使用本地 HTTP 服务时交付可用地址和重启命令，不能只留下已经退出的服务。

文件写入成功、HTTP 返回成功、浏览器标签创建成功，都不能单独代表预览验收完成。浏览器能力不可用时仍保留 HTML，说明验证阻塞，不编造截图或验证结论。

实现保持三个文件：`SKILL.md` 固化工作方法，`agents/openai.yaml` 配置显式调用，本文保存示例调研。示例帮助理解表达方法，不是每次生成都必须重新访问的输入，也不是固定页面模板。
