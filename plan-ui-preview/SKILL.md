# 方案 UI 预览

让读者直接看到改哪里、改完什么样、什么条件下会变化。默认交付**高保真设计稿＋评审旁注＋关键交互**，在本机浏览器预览。高保真指画面完成度接近成品，不等于复刻现状。

仅在用户点名调用本 skill 时使用。不自行接到所有方案后面。输入可以是当前对话、文档或本地文件中的方案；不要求先运行某个规划 skill，也不重新编写业务方案或修改业务代码。

动手前打开 [精细度案例](references/design-cases.md)，选与本次改动结构最接近的一例，在浏览器中按锚点查看参考局部；没有相近结构时，只读其中的通用方法和不迁移项。来源依据、业务映射和冲突处理示例按需读 [示例调研](references/research.md)，无需重复访问其中的远程链接。

## 1. 确定这次要展示什么

- 先读已有方案，确认用户要看整份最终方案，还是某个阶段、某个 PR。只整理该范围的 UI 影响；纯后端且无 UI 改动时说明即可，不硬造页面。
- 优先使用用户指定的现有页面、截图、HTML、组件或设计规范作为视觉基线，再查找当前项目内相关材料。飞书内容优先用可用的 `lark-cli` 和对应文档能力读取；其他来源使用当前环境合适的读取工具，不绑定某个服务。
- 项目基线决定产品画面的外观和数值；精细度案例只示范每个局部要做哪些决定、画出哪些状态，不提供样式。目标项目是浅色时，用参考稿的浅色主题对照；浏览器不可用时，读案例给出的锚点和选择器。
- 用普通清单建立“来源要求 → 页面或区域 → 触发条件 → 结果状态”的对应关系。关注新增、修改、移除，以及同一对象在不同位置、权限、生命周期下的差异；工程内部结构只呈现其可见结果。
- 已有信息能回答的问题自行核对。来源冲突或缺口会改变关键画面、核心操作时先澄清，并继续不依赖答案的部分。小的非关键缺口用明确假设补足，不把评论自动当成已确认需求。
- 现状依据分三档：现状截图或可运行页面；依源码与 token 重建，页首注明未经运行截图核对；缺少可靠依据时标为“设计示意”，不能声称复刻了当前页面，不能编造改前画面。三档的视觉完成度相同；设计示意的尺寸优先取用户指定的组件库或平台规范，并在评审区列出假设。已有基线时保留本次未涉及区域。

## 2. 组织评审页

先展示改动所在的必要环境，再展开局部 UI 和对应旁注。少量改动可以直接展示一处，不必搭完整产品外壳或套固定章节。

- 用字母、编号或短标签连接画面位置和旁注。旁注写具体的“条件 → 变化”，放在产品画面外；来源、假设、争议和模拟说明也放在评审区域。
- 画面数据要让本图条件下的规则真实出现：写了尾部省略，图里就有省略号；写了收起，图里就是收起后的样子。出现后的形态也要设计：截断或收起时保留什么、截到多短仍能辨认、放不下时改用什么形态（只留图标、+N、整颗换行）。可滚动区域的裁切处要有滚动提示；省略和折叠分别保留识别信息或展开入口。
- 同一形态在其他条件下的变化，用旁注、切换或展开说明；形态本身改变时（空结果收缩、折叠、浮层，权限导致控件消失或只读），另画一张或做成可切换。只在有可靠依据且有助于判断时展示前后对比。只补本次改动需要的状态，不穷举无关异常。
- 评审层与产品层分开。评审层（页面标题、分区、旁注、画布外框）采用细线条标题、克制用色，每块画布只保留一层边界，避免 card 套 card。产品层已有部分继承目标项目的组件、字体和视觉规范；新增且没有先例的元素同样细线条、克制用色。不要把示例中的配色、尺寸、明暗切换或业务规则照搬到其他项目。
- 每个关键局部都要做出具体的设计决定：尺寸相对哪个容器、行高或对齐线；少用字号档，主次优先靠字重、墨色和透明度，选中态沿用项目规范，没有先例时优先用对比变化表达；图标出自同一套，线宽、端点和各位置尺寸统一；底、容器、浮层各对应一种边界或阴影，浮层打开时触发对象有打开态；有限宽度内谁让位；列表和浮层贴合、滚动、空结果时的高度。
- 决定落在 CSS 和画面上，不另做参数表。旁注只写影响判断的阈值，如“条件 → 数值或变化”；纯样式数值不标注；改变信息量或可操作性的阈值，方案没写的按第 1 节用明确假设补足，列入评审区。
- 先确定哪些操作会影响本次方案判断，再实现这些关键交互。删除联动、展开收起或状态切换若是改动核心，就必须能操作。视觉细化不能削弱方案要求的关键交互；涉及多个对象、位置或设备的联动，要能操作并观察各方结果，不能用单侧状态按钮代替整条链路。无关控件可仅展示，并在评审说明中讲清边界，不用无效按钮或泛化提示冒充实现。
- 动效默认不要求，但静态的选中、悬停态必须完整，不能只靠动画脚本绘制。方案把动效本身列为改动时，要么能操作，要么在交付中标“动效未演示”，旁注不写成画面已呈现的效果。

## 3. 生成 HTML

默认输出到当前任务的 `artifacts/ui-preview/<topic>/index.html`；用户指定位置时遵循用户选择。保留已有产物，避免覆盖无关文件。

先做一个代表性局部，例如菜单的普通行、选中行、长内容和空结果，在浏览器截图，按第 4 节的视觉细节检查通过后再展开其他画面。单控件或文案改动只截改动处及其上下文，正常和受限宽度各看一次。

- 默认单文件 HTML，内联 CSS 与 JavaScript，无需前端构建。实际素材较多时允许附带资源目录，路径必须随产物可访问。
- 优先使用提供的实际素材和现有组件表现。演示素材、模拟数据和本地状态不能冒充线上结果；不连接真实业务提交、发送、删除或支付。
- 采用当前环境能运行的最小实现，不为评审页引入应用框架、通用组件平台、专用数据协议或预览管理器。确有复用需要再封装。最小实现指技术栈，不降低视觉完成度。
- 字体使用系统回退；关键内容不应依赖外部字体请求成功。检查实际用到的图片、样式和脚本，不让丢失资源被空白占位掩盖。

## 4. 在浏览器中验证

使用当前环境可用的浏览器能力实际打开生成结果。工具和启动方式由运行环境决定，不能只执行文件检查或 HTTP 请求后就声称已预览。

优先直接打开本地 HTML。浏览器需要 HTTP 时，用已有工具启动仅服务产物目录的简单本地服务，默认绑定 `127.0.0.1`。检查实际可用地址，在交付时保持服务运行并给出同一目录的重启命令。远程执行环境使用用户能够访问的预览转发入口，不能把执行机的 localhost 当成用户可访问链接。仅在用户另外要求时发布在线链接。

验收围绕改动清单进行：

1. **画面覆盖：** 每个本次 UI 改动能在具体区域或状态中找到；旁注与画面一致，未确认内容明确标注。
2. **实际呈现：** 查看默认画面和相关边界状态，检查遮挡、溢出、缺图与可读性；按目标界面选择正常及受限宽度，不无条件加做移动端。
3. **关键操作：** 实际触发关键交互，观察对应对象的变化、联动和必要的恢复行为。区分“有实现代码”和“已在浏览器操作通过”。
4. **资源与证据：** 检查可获得的控制台、资源错误，以及可见的加载异常；保留整幅与代表性局部的截图或观察记录。工具看不到的项目不得声称检查过。
5. **视觉细节：** 在目标视口截整幅和代表性产品局部。有基线时与基线同尺寸并排比较样式；精细度案例只比精细度，不比数值。检查同一局部内尺寸、间距一致，对齐线成立，图标出自同一套，表面层次不多叠，主次文字可辨，规则触发后的内容仍可辨认，可滚动区域的裁切处有提示。截断、滚动先用 DOM 确认确实触发（如 `scrollWidth > clientWidth`），再看截图确认可读。每轮记下“位置 → 现状 → 改为”；代表性局部改到通过，整页最多两轮，剩余差异写进交付。

修复发现的问题后复查受影响的行为与画面。浏览器验证受阻时保留 HTML，说明具体阻塞和未验证项；文件生成、HTTP 成功或标签创建成功都不代表验收完成。

## 5. 交付

最终回复以可用结果开头，简短给出：

- HTML 文件链接和可打开的预览入口；必要时附资源目录或打包文件。
- 主要改动所在的区域或锚点，以及已经实际验证的关键交互。
- 视觉检查的视口和截图，以及仍未达标或属于假设的部分；未完成目标视口截图检查时写明“未做视觉验收”，不称为已验收的高保真稿。有现状基线时另做同尺寸对照；无现状基线时按视觉细节清单检查，并保留“设计示意”标识。
- 仅展示、模拟、待确认或尚未验证的部分；使用 HTTP 服务时附实际启动目录与重启命令。

在支持的环境中把预览打开给用户，并保留交付标签。使用真实的路径和地址；不把临时本机服务称为永久在线链接，不把原型交互当作业务实现完成。
