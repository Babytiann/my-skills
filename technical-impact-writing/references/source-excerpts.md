## 2. 方法框架与工具职责

对应分析：第 2、3 节。

「找办法」一节先给出总括，再用四个小标题对应四个动词：建范式：OpenSpec、聚资源：Aime、建流程：流水线 + Trae、控质量：Aime CR。

> 不管是互联网、制造业还是供应链，**资源整合**的本质都是：把分散的人 / 货 / 技术 / 数据，通过标准化规范和流水线化流程，变成可复制、可规模化、可降本增效的稳定产出。都遵循同一个闭环：**定标准 → 聚资源 → 建流程 → 控质量**

并列的两个 callout：

> **OpenSpec：为 AI 协作立规矩**
> - **规范先行**：强制在编码前，将模糊需求转化为清晰、可验证的**提案（Proposal）**、**规范（Spec）**和**任务（Tasks）**。
> - **变更原子化**：每一次功能、重构或修复都是一个独立的、可追溯的**变更（Change）**单元。
> - **知识沉淀**：将开发过程中的决策、设计与最终规范沉淀于代码库，形成“**活文档**”。
> - **智能助手**：辅助人机协同

> **Aime：让规范高效落地**
> - **智能理解**：深度理解 OpenSpec 结构，辅助开发者快速完成**提案、设计与任务拆解**。
> - **精准执行**：严格按照 `tasks.md` 执行编码，杜绝“自由发挥”，保证**代码与规范强一致**。
> - **流程自动化**：自动完成**生成 MR 描述、归档变更、同步规范**等流程性工作，解放生产力。

各工具小节开头用一句话定位，例如：

> **一句话定位**：轻量级开源**规范驱动开发（SDD）框架**，专为 AI 编程助手设计，通过 “先写规格、再写代码” 的结构化流程，让 AI 按明确规范生成代码，实现开发可控、可追溯、可协同

## 5. 协作规则、角色与回路

对应分析：第 4、10 节。

### 5.1 协作要点

> #### 协作要点：
> - **沟通前置**：在 `Proposal` 和 `Spec` 阶段，鼓励 RD、UX、QA 早期介入，充分讨论，避免后期返工。
> - **单一事实源**：`spec.md` 是所有角色对齐需求和验收标准的唯一依据。任何口头、IM 中的需求变更，都必须先落实在 `spec.md` 中。
> - **责任明确**：RD 是从 `Proposal` 到代码实现的核心负责人，主导整个技术交付过程。
> - **UX 自主调参**：对于如图表样式这类频繁变更的配置，建立 UX 可自主修改、验证、提交的流程，将 RD 从中解放出来。UX 交付的不仅是设计稿，更是可直接被代码消费的**配置数据**。

### 5.5 动效开发：痛点与对比

> **核心价值**：通过 AI Studio + Claude Code 的工具组合，让 UX 能够自主生成和微调动效，RD 借助 AI 快速将动效转化为项目可用代码，大幅缩短动效开发周期，减少 UX-RD 之间的反复返工成本。

并列的两个 callout：

> **传统模式的问题**
> - 动效开发耗时长，RD 手写动画代码成本高
> - UX 的动效预期难以精确传达，文字/视频描述存在理解偏差
> - RD 实现后与 UX 预期有出入，需反复调整
> - 每次微调都需 RD 修改代码、构建、录屏、确认，链路冗长

> **AI 协同模式的改进**
> - UX 在 AI Studio 上直接生成动效原型，所见即所得
> - RD 借助 Claude Code 快速将动效代码转化为项目可用样式
> - UX 可基于源码和运行效果进行精确的参数微调
> - 沟通从"描述动效"变为"交付代码 + 可视化效果"，减少理解偏差

动效流程画板转写：

```
UX: 确定动效需求 → UX: AI Studio 生成动效 App → UX: 交付 AI Studio 链接给 RD
→ RD: Claude Code 转化为项目代码 → RD: 运行录屏交 UX 确认
→ ◇ UX: 效果是否符合预期?
     —需微调→ UX: 基于源码提供调整参数 → RD: 调整后再次录屏确认 → 回到判断
     —确认通过→ RD: 提交 MR / CR → 合入代码
```

详细步骤中「⑤ UX 微调参数」一行的结尾：

> **核心改进**：UX 不再只是口述"快一点""幅度大一点"，而是基于实际代码参数给出精确调整值，大幅减少沟通歧义和返工次数。

效果对比：

| **维度** | **传统模式** | **AI 协同模式** |
|-|-|-|
| **动效表达** | UX 通过文字描述 / 参考视频传达动效预期，RD 凭理解实现 | UX 在 AI Studio 直接生成可运行的动效原型，所见即所得 |
| **代码实现** | RD 手写动画代码，耗时且容易与预期有偏差 | Claude Code 自动转化动效代码为项目可用文件，高效精准 |
| **调整效率** | 每次调整需 UX 口述 → RD 理解 → 修改 → 构建 → 录屏，链路长 | UX 基于源码给出精确参数，RD 快速调整，减少返工轮次 |
| **动效质量** | 受限于 RD 对动效的理解，最终效果可能与设计预期有差距 | UX 主导动效生成，RD 负责工程化落地，最终效果更贴合设计意图 |

## 6. 证据与取舍

对应分析：第 11 节。

CR 工具对比：

| 工具 | 优势 | 劣势 | 适用场景 |
|-|-|-|-|
| **Aime CR** | 准确率高，功能全面 | 需手动触发 | 全量需求，重点需求的深度检查 |
| **Aime CR & fix** | 自动修复功能强大，提高提测质量 | 修复效果可能影响开发效率 | 代码质量要求极高的项目 |
| **Aime CR & 评论** | 自动在MR中添加评论，提高问题可见性和被关注度 | 评论过多可能造成干扰 | 团队协作密集的项目 |
| **Bits** | 生产系统默认执行 | 默认执行准确率不高 | 静态分析为主 |

> **轻重结合**：并非所有 MR 都需要最深度的 CR。对于简单的配置修改或文档更新，可以使用轻量级检查；对于核心业务逻辑的变更，则应开启所有检查项，并结合人工评审。

按规模区分的建议（自动化流程一节）：

> - 中大项目：包括初步技术方案生成、缺陷自动汇报、自动CR模版配置
> - 小型项目：可以直接绑定 openSpec 开发
