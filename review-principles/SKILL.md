# 代码评审视角与原则

评审要回答三件事：这次改动能不能合入，合入前必须改什么，哪些事要 owner 拍板。判断依据是这个项目自己的原则，不是评审人的口味。

仅在用户点名调用时使用。评审对象可以是 PR、分支、diff、本地改动或技术方案。默认用中文写，读者是作者和 owner。只评审，不顺手改代码；用户另外要求时再修。

各视角的检查项、常见信号和例子见 [评审视角清单](references/perspectives.md)。方法提炼自哪几篇评审、每条检查项出自哪一节，见 [来源笔记](references/research.md)；不需要重新读取原文。

## 1. 确定范围与深度

开始前一次问清；能从对话和仓库里查到的，不问。

- **对象与 commit**：评审哪个 PR、分支、diff 或方案；固定被评审的 head commit 和对比基准（如 `git diff A B` 中 B 是 head，A 是基准），后文所有结论都基于 head。
- **深度**：
  - **标准（默认）**：按第 3 节的表选视角，用户原则里点名的问题（如重构、过度设计）对应的视角也要看；发现明显问题时可以加看其他视角，在「范围与证据」里写明加了哪个、为什么。至少在当前开发机上跑通日常路径（文档类改动就照着文档走一遍关键步骤），其余实测按需。改动碰到平台敏感代码时，按第 5 个视角读代码检查，结论标「代码」或「推断」；其他平台和远程链路写明「未覆盖」。不额外询问环境。
  - **最全面**（用户明确要求时）：看全部适用视角；日常路径和边界都实测；多端产品做远程实测，一台机器上就能搭；做跨平台验证。
- **最全面时，跨平台验证先问用户**，和其他范围问题一起问：
  1. 产品的目标平台有哪些：macOS、Windows、Linux 各自的系统版本下界和 CPU 架构。
  2. 用户能提供哪些环境：另一台实机、虚拟机（如 Parallels、UTM、OrbStack、Lima）、Windows 上的 WSL、可 SSH 的主机；怎么连，有什么权限。

  只用用户提供的环境，不自行安装系统、创建虚拟机，也不改用户的日常环境。没提供环境的平台标「未覆盖」，并在附录给出该平台的补测清单。写明环境的局限：WSL 既不是原生 Windows，也不是有桌面会话的 Linux（比如没有钥匙环）；虚拟机里的性能数字只作参考。

## 2. 先定准绳

读代码之前，先确定拿什么衡量。来源优先级：本次对话里用户给的原则 > 项目文档（AGENTS.md、CLAUDE.md、SPEC、设计文档、用户确认过的行为）> 从仓库现状推断。在「范围与证据」里写明本次采用的原则。

准绳分三层：

- **阶段立场**：在最佳实践和兼容现状之间偏向哪边，防御做到什么程度。一个内部开发期项目的原则示例：

  > 我们目前处于内部开发阶段，没有真实用户。任何不是最佳实践的代码实现和架构设计，后期影响都会很大。不要担心兼容现有设计，尽量对齐最佳实践；只要不是过度设计，允许抽公共部分和重构。但不要过早过度防御，处理过于边角的情况，往往会成为后续架构优化的负担。

  已有真实用户的项目通常相反：兼容、迁移、灰度、回滚是一等问题，针对真实输入的防御是合理的。
- **产品前提**：代码必须守住的产品不变量。以一个「本地 daemon 加多台配对设备」的产品为例：断连是常态；所有设备背后是同一个人，不需要 merge，但断线旧设备的迟到写入是真的；用户第一，用户正在编辑的内容不能被悄悄发出旧版；调用方不只是人，agent 经 CLI 操作时要有对等能力，拿得到 id，来源被记下。目标平台也属于前提。每条前提都转成检查项；改动不涉及某条前提时，在「对照项目原则」里写「不涉及」。
- **规格依据**：SPEC 和用户确认过的行为。每条发现都写明违反了哪一条准绳。

阶段立场或产品前提缺失时：能从 README、SPEC、skill 说明等材料推出来的，写成「推断的前提」并标出；推不出来、又会改变结论的，问一次，和第 1 节的问题一起问。不悄悄套用通用的「最佳实践」。

立场会改变判断：

| 问题 | 内部开发期 | 已有真实用户 |
|---|---|---|
| 不是最佳实践的现有设计 | 建议直接改到位，不以兼容为由保留 | 评估迁移成本，给出渐进路径 |
| 抽公共部分、重构 | 有真实复用或明显降低复杂度就做 | 同样可以做，但拆成独立改动，控制风险 |
| 边角防御 | 不要求；为不存在的情况写的防御本身算问题 | 真实用户会遇到的输入要处理 |
| schema、协议、持久化格式 | 可以直接改 | 要有迁移、版本和回滚 |

**过度防御和必须修怎么分**：按「窗口 × 后果」判断，不按「理论上会不会发生」。日常路径上的失败、丢数据、卡死、违反不变量，必须修，不算边角。要小概率组合才触发的情况、系统到不了的状态、为从未出现过的问题写的回退，算过度防御。内部开发期的建议是删掉这类代码；不变量真被破坏时大声失败（记 error），不默默容忍。窗口窄、后果轻的，放进「已考虑、不建议修」。

## 3. 评审视角

1. **准绳与日常路径**：先确认最常走的路径跑通，作为参照，也让后面的结论可信；再对照规格查行为，核对注释和文档的说法与代码是否一致。
2. **状态机、时序与不变量**：画出状态和转移，查清每个状态由谁写；找竞态和窗口、拆卸顺序、靠「一边消失、另一边出现」的交接、由竞态决定的终态。优先收成一个不变量、一个写入点。
3. **失败、恢复与耐久**（单个节点上）：重启后什么只存在内存里；强杀后已经对用户承诺的数据还在不在；超大输入和各层上限；等待和写入有没有时限；报错是否指对了方向和范围。
4. **远程、多端与同步**：远程链路与本机链路的差异；半开连接与丢应答；一台离线时另一台动了同一个对象；幂等 id 和去向活多久；重连收敛与唯一时序来源；状态该按设备存还是跨端一致；离线期限与离线创建；交接空当按往返放大，多个窗口只出一份副作用。产品有多个设备、窗口或客户端，或客户端和权威端之间隔着网络时看。
5. **跨平台与运行环境**：平台门控与版本下界；进程与信号的平台差异；同一 API 在各平台的支持承诺；原生依赖与工具链；权限与凭据存储；文件系统、路径与脚本；快捷键与呈现；性能和测试结果不跨平台外推。产品面向多个操作系统，或改动碰到平台敏感代码时看。
6. **调用方与契约**：覆盖每种调用方（UI、agent CLI、脚本）；返回形状按调用方真正会分支处理的结果定；瞬时的过程状态不进 DTO；结果带判别字段；退出码一码一义，「下一步」提示与之相符；等待有超时；不想阻塞的调用方有不阻塞的确认方式。
7. **用户感知与下游反应**：人看到的是否如实：停下就是停下，主动停止不显示成失败，文案指对原因，输入框清空后字不丢，失败有反馈。再往下看一步：拿到这个输出的人或 agent 接下来会做什么。
8. **结构与扩展成本**：同一条规则散在几处；模块互相伸手；可选依赖编译能过、运行才报错。问「下次加一种发送方、原因或实现，要改几处」。多个同根的问题收成一条规则。
9. **过度设计与复用**：逐个机制判断保留、简化或删除，并写出行为变化；查平台内置能力、仓库已有实现、成熟的库；删死代码、走不到的分支、重复代码、多余的索引、客户端能自己算的字段。第二个真实使用者出现之前不推动抽象，记一笔即可。
10. **性能、资源与生命周期**：按真实规模测，用对照实验找出开销在哪，给出验收预算；子进程在退出前一直持有引用，终止逐级升级，应用退出时有收尾；停止路径没有死锁；订阅能释放；写入有时限。讲比例：毫秒级的开销改注释即可。
11. **注释、文档、测试与 PR 卫生**：注释自包含，不抄别处定义的列表和常量；PR 描述会成为提交说明，必须准确；用户文档的承诺经得起实测；测试覆盖出过问题的场景，名实相符，不依赖机器快慢；纯移动的重构不混进功能改动。文档本身就是产品时（skill、提示词、runbook），同一个术语只有一个意思，每条指令能执行、有完成判定。

按改动类型选重点：

| 改动类型 | 重点视角 |
|---|---|
| 任何改动 | 1、11 |
| 队列、协议、状态流转 | 2、3、4、6 |
| 同步、复制、发件箱、连接、配对 | 3、4 |
| 原生代码、子进程、文件系统与路径、shell 脚本、构建与打包、快捷键 | 5、10 |
| 纯 UI | 7、10、11；涉及多窗口或多设备时加 4 |
| 新增原生或基础设施依赖 | 5、9、10 |
| 文档、提示词、skill、runbook | 1、7（读者或下游 agent 照做会怎样）、8（同一规则散在几处）、11 |

最全面时看全部适用视角。产品前提里有「远程、多端、离线」时，第 4 个视角必看，要有远程实测或写明未测。产品面向多个操作系统时，第 5 个视角同理：标准深度下读代码检查，最全面时在用户提供的环境里实测。

## 4. 证据

- 每条结论标注 **实测**（在运行环境里复现）、**代码**（读代码可确认）或 **推断**（依据 API 行为或公开资料，尚未复现）。读代码或推断得出的结论，不写成实测。文档类改动：用脚本核对链接、锚点、行号、数值算「代码」；照着文档实际走一遍、或在浏览器里看到结果算「实测」。
- 写明实测环境和它的边界：覆盖了什么，哪些没覆盖，为什么。只在本机链路上测过，就不能写「远程与本机一致」。
- 多端产品区分本机实测和远程实测。远程结论要经过真实配对、走能模拟故障的代理，设备和服务端不共用数据目录；做不到时标「远程：只读代码」。「一台离线、另一台操作同一个对象、再重连」这类组合要单独测。
- 跨平台结论带上平台和版本，如「实测（Windows 11）」，不外推到其他平台。目标平台缺少原生组件时，可以用按同一协议输出的模拟进程代替，并写明模拟覆盖了什么、没覆盖什么。
- 在隔离环境里测（独立的 home、端口、profile），不碰用户的日常环境。测试工具产生的截图、快照、日志写到仓库外的临时目录；结束时关掉自己起的服务，确认 `git status` 和开始时一致。结论取决于第三方行为时，写一个最小探针直接测它。
- 数字附上测量方法。竞态类写明试了几次；没复现出来就照实写。
- 代码位置写函数或符号名，文档位置写「文件 + 章节标题」；行号只和固定的 head commit 一起给。head 变了，复读中间的改动，给每条结论标「新增、更新、不变」。

## 5. 严重度与结论

- 严重度按用户能感受到的后果定义，在开头按项目调整。默认四档：
  - **严重**：丢数据、发不出去也撤不回、卡住、用户放下的东西自己又跑起来；
  - **一般**：和规格不一致，或会误导人；
  - **轻微**：文案、边角情况；
  - **设计**：眼下不出错，但结构上会让下一次改动出错。

  文档、提示词类改动可以这样对应：严重 = 照做会产出错误或虚假的交付、或卡住；一般 = 与其他指令矛盾，或逼执行者猜；轻微 = 措辞；设计 = 重复或结构会让后续修订走样。需要时映射成 P 级：严重 → P1，一般 → P2，设计 → P2 或 P3（看下一次改动有多近），轻微 → nit。
- 结论写 Approve 或 Request changes，并列出「合入前必须处理」。评审已合入的提交时，结论写「保持」或「需要后续修订」，清单改叫「下次修订必须处理」。
- 「已考虑、不建议修」列出看过、但不建议改的情况和理由：窗口窄、后果轻、规格明文如此。这既说明覆盖面，也避免之后反复讨论。
- 「做得好的地方」写具体、验证过的做法，不写客套话。

## 6. 一条发现怎么写

按这个顺序写，不必写成固定小标题：

> 怎么触发（真实场景、有多常见）→ 现在会怎样（观察到的现象，带标注）→ 为什么（根因机制，指到代码符号或文档章节）→ 后果 → 建议（符合立场的最小具体改法、位置和大致改动量）→ 验收（怎么判断修好了）

- 抓根因，不停在现象。几条发现同根时，合并成一条规则，再分别说明各自的入口。
- 建议具体到能动手。有明显但错误的修法时，写出「不建议的做法」和理由。
- 检查各条修法之间的影响，排好先后。例如，一条修法让发件箱等到复制确认后才收尾；如果服务端在消息离开队列后就忘掉它的 id，这条修法会把补发变成新消息，所以要先解决 id 的问题。
- 修法和规格或有意钉住的测试冲突时，交给 owner，不悄悄推翻。

## 7. 交给 owner 的决定

产品和语义上的取舍集中放在一节，每条写清问题、选项 (a)/(b)、推荐项和各自的后果。评审人可以建议，但不替 owner 决定；也不能什么都不说，默认按一种做。

## 8. 输出

篇幅随改动大小伸缩，不为凑结构填空节。完整骨架：

1. 结论：Approve 或 Request changes，三五句说明，加「合入前必须处理」。
2. 范围与证据：对象与 commit、深度、所选视角、方法、环境与边界、覆盖和未覆盖的平台、标注说明、严重度定义、所用原则。
3. 省流表：编号、问题、严重度、依据、建议。
4. 按严重度展开的发现。
5. 结构与过度设计专项。
6. 对照项目原则：受影响的前提逐条写影响；不涉及的合成一句，列出名字。
7. 已考虑、不建议修。
8. 做得好的地方。
9. 需要 owner 拍板。
10. 推进顺序：按修法之间的依赖排。
11. 附录：复现步骤、代码位置、未覆盖平台的补测清单。

精简版（改动约 200 行以内，或只涉及一两个视角）：结论（含必须处理）→ 范围与证据（几行）→ 按严重度的发现 → 需要 owner 拍板（有才写）。纯设计评审的发现可以按「前提 → 设计问题 → 实现问题」组织。

默认在对话里交付；超过约 150 行、且用户没要求只在对话里给时，写成 markdown 文件并给出路径；用户要求时，用 `lark-doc` 写成飞书文档。用具体场景说话；术语第一次出现时，说明它在这里指什么。

## 9. 复核别人的评审

用户要求复核一份已有评审时：不复述证据扎实的发现；重点找环境和范围造成的盲区（只测了本机链路、只测了一个平台）、与实测矛盾的结论、彼此有影响的修法。结尾给出编号的修订建议。
