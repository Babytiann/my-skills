# 评审视角清单

先按 `SKILL.md` 第 3 节的表选视角，再到这里找检查项。检查项是提示，不是要逐条作答的表格；和改动无关的跳过。例子改写自来源评审，只说明问题长什么样，不是其他项目的事实。

## 1. 准绳与日常路径

**看什么**
- 最常走的几条路径是否按规格跑通；把跑通的路径和证据列出来。
- 行为是否符合规格依据和用户确认过的行为；规格自身有矛盾时指出来。
- 注释、内部文档、用户文档、PR 描述的说法和代码是否一致。
- 规格接受过的已知限制，它们的前提现在是否还成立。

**常见信号**
- 注释写着「不会发生」「已经被挡住」，挡住它的条件却有例外。
- 一条规则依赖另一处的保证，而那处保证有缺口。

**一例**：运行时的能力检查被删掉了，理由是「低于最低版本的 CLI 已被版本门挡住」。可版本门对读不到的版本号一律放行，于是旧版 CLI 上每一轮都结束不了，后面的消息全部挂着。评审建议改看能力声明，不看版本字符串。

## 2. 状态机、时序与不变量

**看什么**
- 每个对象有哪些状态，谁能触发转移；每个状态有没有出口，有没有谁都处理不了的状态。
- 同一件事是否只有一个写入方、一个写入点；「谁负责结算」是否散在多处，各自带开关。
- 并发和窗口：逐个处理一组对象时，前面的已经处理、后面的还没轮到，这段时间里会发生什么。
- 卸载、出错退出、归档、关闭等收尾路径的顺序是否一致。
- 组件之间是按同一个 id 连续变化，还是靠「一边消失、另一边出现」交接。
- 终态取值是否由竞态决定（同一种停止，有时记 cancelled，有时记 interrupted）。

**常见信号**
- 注释承认结果「取决于调用方控制不了的竞态」。
- 一个对象的状态机拆在两个文件里，靠十几个回调互相改状态；「走到哪一步」有好几份记录。
- 现在正确，是因为几个超时刚好错开。

**一例**：用户停下一棵会话树后，有四个入口能把它重新叫醒：树里的 agent 发消息、provider 自己开轮、恢复归档、被停的报告轮重送。逐个修容易漏，评审把它们收成一条规则：「被人放下的会话，在人开口之前保持安静」，再逐个说明每个入口怎么落到这条规则上，以及为什么不建议「先停叶子」这类做法。

## 3. 失败、恢复与耐久

**看什么**
- 服务端重启后，哪些等待、唤醒、订阅只存在内存里；哪些持久化、哪些不持久化，是否有意区分，有没有文档说明。
- 强杀（崩溃、被系统杀掉、断电）后：输入框已经清空、对用户承诺过「不会丢」的数据，是否真的落盘。
- 超大输入：按发送时是否按各层上限预检；从本地存储复活时是否做同样的校验，过不了的放回给用户，而不是悄悄丢掉。
- 每个等待、每次写入是否有时限；超时之后状态能否恢复。
- 报错的方向和范围：本机发出的内容超限，是否被说成对方数据过多；一条消息出错，是否让整条连接、整台机器都不可用。
- 失败后用户手里有没有出路（撤回、重试、放回），出路是不是只出现极短的一瞬。

**常见信号**
- 持久化依赖 localStorage 这类「过一会儿才落盘」的存储。
- 连接失败后立刻用同一个 id 重发，没有退避。
- 注释写着「唯一的出口是人按 Stop」。

**一例**：粘贴超过 1MB 的文字发送后，连接每秒断开重发约 50 次，撤回按钮每次只出现约 20 毫秒，重启 App 后循环照旧。评审建议进发件箱前按上限预检，从本地存储复活条目时做同样的检查，超限的放回输入框。

## 4. 远程、多端与同步

**看什么**
- **链路差异**：远程链路的单条上限、存活检测时长、加密层、relay 或 SSH 通道，和本机链路有什么不同；凡是写「与本机一致」的，有没有远程实测支撑。
- **半开与丢应答**：网络已断、连接还没判死的那段时间（存活检测的间隔加上等待时间），界面显示什么，用户能不能撤回；判死要多快，按移动链路来定。
- **多端操作同一对象**：一台设备离线时，同一个人在另一台上撤回、放回、编辑了同一个对象；离线那台重连后用原 id 重交，服务端怎么答。
- **id 与去向的生命周期**：服务端是否只在数据行还在时认得这个 id；对象离开后的去向（记入、放回、退回、丢弃）能不能在重连时补给离线设备，能不能活过重启，保留多久。
- **收敛与时序**：重连时补的是权威快照，还是只补数据行；有没有用设备时钟排序（时钟不准，后改的会输给先改的）；单用户不需要 merge，但迟到的旧写入不能覆盖新的；每次变化是否都全量重传。
- **状态归属**：哪些状态按设备存是对的（如按机器授予的系统权限），哪些应该跨端一致却存在了本地（如默认发送方式）；发送中、正在编辑、「这个 id 我撤回过」这类状态只在页面内存或单个视图里时，刷新、重启、换视图后是否还对。
- **离线期限与离线创建**：发件箱里的东西过多久就不该再自动发出；离线新建、首条消息、会话内追加，三条路对「按了发送然后断了」的处理是否一致。
- **交接空当与多窗口**：本机量到的几十毫秒闪烁，在远程要按往返时间放大；多个窗口共享状态时，副作用（子进程、提示）是否只出现一份。

**常见信号**
- 去向只推给当时在线的设备一次；重连只补数据行。
- 冲突处理靠逐行版本号加回传内容，产品却只有一个用户。
- 「正在编辑」只是客户端的组件状态，服务端不知道，照常派发旧内容。
- 远程相关的结论全部来自读代码。

**一例**：一台远程设备发出消息，服务端收下了，应答却丢在路上。用户在另一台电脑上把这条撤回、改写、重发。远程设备过一阵重连，用原 id 再交一次；服务端早已忘了这个 id，当成新消息收下，Agent 同时收到改写后的话和原话。三种操作路径都能复现。

**远程实测环境**（一台机器即可）：
1. 服务端用独立的数据目录，起在本机一个端口上。
2. 起一个 TCP 故障代理转发到服务端，支持透传、挂住、只丢下行、断开、按方向冻结和延迟。
3. 服务端对外只公布代理的地址，让配对出来的设备只能经过代理连接。
4. 设备用另一份数据目录和独立的应用 profile 启动，走正常配对。不能和服务端共用数据目录，否则会被当成本机连接。
5. 需要两台远程设备时，再起一个实例。
6. 测「一台离线、另一台操作、再重连」：把其中一台的代理切到断开或只丢下行，在另一台上操作，再切回透传。

## 5. 跨平台与运行环境

**看什么**
- **平台门控与版本下界**：不支持的平台不出现入口、不拉起进程、不编译原生代码；系统版本判断放在一处，再告诉其他层；参数缺失时，各项能力的默认值方向是否一致。
- **进程与信号**：信号语义各平台不同；应用退出时子进程由谁回收（Windows 可能由 job object 兜底，macOS 没有）；停止之后，是否等到进程真正退出才放手。
- **平台 API 的承诺**：同一个 API 在各平台的官方支持程度不同，按目标平台查文档和已知 issue；只有一个平台给了承诺的路径，在其他平台实测之前不能依赖。
- **原生依赖与工具链**：原生模块、可选的原生优化在各平台、各架构上能否加载；新增的平台工具链是否写明；dev、build、打包是否都覆盖。
- **系统能力与权限**：权限模型（如 macOS 的隐私授权）、凭据存储（钥匙串、Windows 凭据管理器、Linux keyring）、通知、托盘与 Dock；权限弹窗出现的时机和文案说的是否一致。
- **文件系统、路径与脚本**（补充）：路径分隔符、大小写敏感、路径长度、可执行位、文件锁、换行符；npm 脚本和 shell 片段在 Windows 上能否运行。
- **交互与呈现**：快捷键（⌘ 与 Ctrl）、字体回退、DPI 缩放、窗口控件；原生快捷键要单独验证，不能用脚本触发代替。
- **性能与测试**：一个平台的性能数字不外推到另一个平台；CI 是否覆盖目标平台；完整测试套件在各平台能否在合理时间内跑完。

**常见信号**
- 注释写「Node 和 Chromium 都做不到」，实际上某个平台已有内置实现。
- 「退出后没有残留进程」只在一个平台上测过。
- 构建脚本只在 dev 下编译原生组件。

**一例**：评审在 Windows 上测一个「关闭 stdin 后不退出」的 helper，应用退出时两个进程都被回收了，这是 Windows job object 的行为。macOS 没有这层兜底，同样的代码会留下持有系统音频的孤儿进程。评审把它记成实测问题，并在 Mac 补测清单里列了「退出后的残留」。

**向用户要环境**：问什么见 `SKILL.md` 第 1 节，只在最全面时问。问的时候说明两件事：只用用户提供的环境；没有环境的平台标「未覆盖」，并附补测清单。

环境的局限要写进评审：
- WSL 不是原生 Windows：Windows 原生的界面、文件系统语义、进程回收都不在 WSL 里。它也不是有桌面会话的 Linux，默认没有钥匙环。
- 虚拟机里的性能数字只作参考；GPU、音频设备、蓝牙等硬件行为可能和实机不同。
- 一台机器上的多个实例模拟多台设备，不等于多台物理设备。

**补测清单的写法**：每行写「项目 → 操作与判定」。操作要能照着做，判定要能看出过没过。

| 项目 | 操作与判定 |
|---|---|
| 停止与退出 | 持续运行时反复关闭、隐藏、退出；退出后不应残留子进程，有残留就抓线程栈看卡在哪 |
| 输出设备切换 | 运行中切换内置、USB、蓝牙设备；数据应持续，采样率正确 |
| 原生性能 | 在真实规模的数据下，分别测各进程 10 秒内的 CPU，对照开启、静音、关闭三种状态 |

## 6. 调用方与契约

**看什么**
- 列出所有调用方：人（各端 UI）、agent（CLI）、脚本。每种都能完成该做的操作（发送、撤回、编辑、列出），拿得到后续操作需要的 id；来源在受理时记下，派发时继承。
- 返回形状按调用方真正会分支处理的结果来定：没人在运行时切换的参数删掉；调用方分不清的两种结果合并；瞬时的过程状态不进 DTO。
- 联合类型有判别字段；同一族命令的输出规则一致（比如是否在管道下自动输出 JSON）；「下一步」只有一种形状。
- 退出码一码一义；「结果不明，别重发」只给真的有一条去向不明的消息时用；给出的下一步，对这个退出码的每种情况都成立。
- 每个阻塞等待都有超时；不想阻塞的调用方有不阻塞的确认方式。
- 重试安全：命令重试时，作用的对象是否不变。不带 id 的「撤回最新一组」，重试时会撤走另一组。

**常见信号**
- 四个接口各有一套结果词，加起来二十个，调用方只对其中七个做不同的处理。
- 客户端代码里有一个 throw，专门处理按配置根本收不到的结果。
- guide 让 agent 按退出码分支，同一个码却捆了几种下一步。

**一例**：daemon 没起时，CLI 什么都没发出去，却以退出码 3 退出；guide 对 3 的说法是「结果不明，去查，别重发」，输出里也没有可查的 id。评审建议按「有没有一条去向不明的消息」来分：连接没建立给「现在不行」，观察中途断线给「继续等」，只有带 id、去向不明时才给 3。

## 7. 用户感知与下游反应

**看什么**
- 用户的意图有没有被尊重：停下就是停下；正在编辑的内容不会被旧版抢先发出；放下的东西不会自己又跑起来。
- 状态标签是否如实：主动停下的不显示成「失败」，也不进「需要你」；只有没人要求的中断才提醒。
- 文案是否指对了原因和方向；有没有漏出未翻译的内部错误；一条提示会不会被另一条盖住。
- 输入框清空之后，字在任何时候都不能丢（断线、强杀、重启）。
- 失败时有没有反馈；按钮一直转圈时，用户知不知道在等什么、能不能撤。
- 往下多看一步：拿到这个状态或通知的人、agent，接下来会做什么。

**常见信号**
- 发送键一直转圈，没有「等待连接」，也撤不回。
- 退回的消息和已送达的消息样式几乎一样，只靠一行灰字区分。

**一例**：用户按 Stop 停下一棵会话树，接着给主 Agent 发「先别做那个了，改做 Y」。主 Agent 处理完这句，又连着收到两条停下前欠着的通知，于是回头问用户「要不要重新派出那条消息」。每段代码都按设计运行，但用户已经改了方向，还得再回答一遍。

## 8. 结构与扩展成本

**看什么**
- 同一条规则散在几处、各自实现；收成一个不变量、一个写入点以后，能删掉哪些参数和约定。
- 下次加一种发送方、投递方式、原因或实现，要改几处；改漏了，编译能不能发现。
- 模块之间是否互相伸手（A 调 B 的回调，B 又直接读 A 的数据）；可选依赖没接上时，是否编译能过、运行才报错。
- 完成一个操作是否要跨太多模块。
- 几个问题是否同根，能否一起修。

**常见信号**
- 一次改动新增了四十多处「是人还是 agent」的判断，背后的五条规则，没有一条有自己的位置。
- 「能不能撤回」在数据库约束、一处字面量和一处判断里各写了一遍。
- 新增一种「需要你」的原因，要手工穿过四个模块。

**一例**：「绑在某一轮上的消息由谁结算」散在七八处，有的跳过「撤回中」的消息，有的不跳，正确性靠几个超时刚好错开。评审建议收成一个不变量：消息不能绑在已经不在运行中的那一轮上。在一轮离开运行态的几处统一结算，就能删掉一串靠调用方各自记住的参数。

## 9. 过度设计与复用

**看什么**
- 逐个机制追问：它是被真实约束逼出来的，还是为不存在的场景准备的？给出保留、简化或删除，并写出改动后的行为变化。
- **平台内置能力**：平台或框架是否已经提供同等能力。内置能力有已知问题时，列一个小 spike（验证哪几项、怎样算通过）和决策规则（通过就改用内置；不通过就保留现方案，并在注释里写明原因）。
- **仓库已有实现**：子进程收尾、消息通道、重试循环等，仓库里是否已有一份可以复用，或者值得抽成公共件。
- **成熟的库**：手写的算法（如 FFT）有没有许可合适、长期稳定的实现可用。
- 死代码、走不到的分支、事务内的重复校验、多余的索引（已被某个唯一索引的前缀覆盖）、客户端能自己算出来的应答字段、编译器已经负责的手写 memo。
- 反过来：第二个真实使用者出现之前，不推动抽象，记一笔即可。

**常见信号**
- 为多人协同设计的冲突合并，用在只有一个用户的产品上。
- 一个被作者自己称作「玩具」的功能，带进来一整套原生工具链和常驻子进程。
- 注释给出的理由（「effect 依赖需要稳定引用」），对比一下编译产物就不成立。

**一例**：一个功能自建了原生 helper、IPC 通道和手写 FFT，约占改动的一半。评审指出框架内置的屏幕共享音频在同一平台用的是同一套系统能力，但有一个未修复的已知问题，于是给出约半天的 spike 清单和决策规则：关键两项通过，就改用内置方案，删掉约一千行；不通过，就保留 helper，按清单修好，并把「为什么不用内置」写进注释。

## 10. 性能、资源与生命周期

**看什么**
- 按真实规模测（长会话、大列表），不按 demo 规模测；写明测量方法和采样时长。
- 用对照实验找出开销在哪（临时去掉某一层，看数字怎么变）；给出验收预算，并建议加回归门槛。
- 热路径上的全量扫描、屏幕外的无效更新、重复做了两遍的平滑或计算。
- 子进程：收到退出事件之前一直持有引用；停止逐级升级（先请求退出，超时再强制）；应用退出时有收尾；新进程要等旧进程退出再启动。
- 停止路径会不会死锁（在被占住的队列里同步等待回调结束）。
- 订阅、监听、定时器能否释放；拆卸顺序和卸载顺序一致。
- 讲比例：毫秒级、量级也不会增长的开销，改注释或记一笔即可。

**常见信号**
- 每秒几十次给所有元素写样式，包括已经滚出视口的。
- 停止时先清空引用，再等进程自己退出。
- 只在小数据量下测过。

**一例**：一个随音频跳动的动画，在 12 条消息的会话里占掉 renderer 主线程约 38%；150 条消息时，每 10 秒有 9.4 秒被占。临时去掉 CSS transition 后降到 2.1 秒，说明大头在不断重启的过渡动画。评审建议只动视口内的元素、只保留一层平滑，并定下验收预算：150 条消息发声 10 秒，主线程忙碌低于 1 秒。

## 11. 注释、文档、测试与 PR 卫生

**看什么**
- 注释自包含：不引规格章节号、PR 号、人名、URL；不拿「别的工具也这么用」当论据，直接写清约定。
- 注释不抄别处定义的列表或常量值，而是指向定义它的地方；已经抄了的，检查是否已经漂移。
- 注释、内部文档、用户文档是否和代码一致；用户文档的承诺（「重启不受影响」「不会变成两条」）经不经得起实测；中英文镜像是否同步，有没有译反。
- PR 描述会成为 squash 后的提交说明：有没有引用读者打不开的东西，事实是否已经过时；标题是否符合仓库规范。
- 测试：出过问题的场景有没有测试；跨实现都要守的规则有没有合规测试；测试名和内容是否一致；夹具有没有造出系统不可能出现的状态；脚手架是否到处复制、已经走样；断言是否依赖机器快慢；有没有测试钉住了错误行为（交给 owner 确认）。
- 改动卫生：纯移动的重构不混进功能改动；把 review 意见逐条抄成 TODO 的，要修掉真 bug、关掉不成立的、对其余的明确取舍，不能删掉注释了事；基线落后时 rebase 到真实基线，让 CI 跑在真实基线上。
- **文档即产品**（skill、提示词、runbook）：同一个术语只有一个意思；多个文件之间谁是权威写清楚；每条指令能执行、有完成判定，循环有上限；引用的锚点、行号、数值能核对；各文件给出的回退路径一致。

**常见信号**
- 注释里出现「见 SPEC §x」或评审讨论的编号。
- 用户文档写成了退出码手册，还写进了屏幕位置和网络细节。
- 一个功能改动显示 +5000 / −4500，大部分是测试文件的移动。
- 同一个词在一份 skill 里指两三样东西；同一条规则在三个文件里各写一遍，措辞已经不同。

**一例**：评审随机抽了 68 个新测试的名字，8 个比测试实际做的窄，4 个说了测试没做的事；收尾清理在 12 个集成测试文件里抄了 14 份，其中 9 份没等应用关完就结束了。

## 评审人的做法

- 以准绳为准，不以口味为准；每条发现都能指回一条原则、前提或规格。
- 先跑通日常路径，再找问题。
- 往下游多看一步：这个输出被谁拿走，接下来会发生什么。
- 「有代码」不等于「已验证」，「实现了」不等于「实际操作通过」。
- 讲比例：把功能的价值和它带来的成本放在一起看，把修法的代价和问题的后果放在一起看。
- 范围外的问题单独记为「范围外，另开」，不混进本次结论。
