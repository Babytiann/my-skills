## 方法论总览

这套方法论把几类成熟框架压缩成一条可复用闭环：用 Double Diamond 先找对问题，用 PDCA 小步推进，用 V&V 思路把需求、验证与验收写清楚，用 SLO/DORA 风格指标同时看速度和稳定性，再把治理、测量与风险管理嵌入全过程。

核心原则：先定义好 `B`，再把 `A -> B` 变成可拆解、可验证、可度量、可复盘的系统。目标不是一次把事做完，而是让项目能按步骤推进、持续变好，并把失败沉淀成规则。

缺省假设：行业、团队规模、时间预算、工具栈、监管要求均未指定时，阈值与节奏只能作为示例标准，落地时必须按项目上下文校准。

浓缩口诀：

```text
定结果，找真因，写标准，拆阶段，设质量门，小步跑，看指标，做复盘，沉规则。
```

闭环图：

```mermaid
flowchart LR
    A[定义 B] --> B[发现真实问题]
    B --> C[写清需求与约束]
    C --> D[拆阶段与接口]
    D --> E[设置质量门]
    E --> F[小步执行]
    F --> G[用指标监控进展与风险]
    G --> H[复盘并沉淀规则]
    H --> B
```

## 八步流程模板

| 步骤 | 每步要做什么 | 主要产出物 | 关键问题 | 常见失败模式 | 可量化指标 |
|---|---|---|---|---|---|
| 定义目标状态 | 用一句话写清楚 B 是什么，不是“做什么”，而是“达到什么结果状态” | 项目 Brief / 目标定义 | B 的完成状态是什么？谁来判断成功？ | 把交付物当结果；目标过大或过模糊；没人拥有验收权 | 目标清晰度评分；目标是否有 owner；目标是否有截止日 |
| 发现真实问题 | 先理解问题来源、用户、上下游、限制条件，不要直接跳方案 | 问题陈述 / 现状地图 | 真问题是什么？证据是什么？如果不做，代价是什么？ | 直接开做；把症状当根因；只听单一角色 | 访谈/证据条目数；问题重述次数；关键假设数 |
| 写清需求与约束 | 把模糊目标翻译成需求、边界、约束、风险和不做项 | 需求清单 / 约束清单 / 风险清单 | 需求是否清晰、独立、可测、可追踪？ | 需求混杂“做什么”和“怎么做”；漏掉边界条件；成功标准不可测 | 需求唯一编号率；可验证需求占比；风险登记完整率 |
| 拆阶段与接口 | 把 A -> B 拆成几个阶段，写清每阶段输入、动作、输出、责任人与依赖 | 阶段图 / RACI / 接口表 | 哪些阶段必须串行？哪些可以并行？阶段之间如何交接？ | 粒度过粗；阶段之间没有交付规范；责任不清 | 阶段定义完整率；依赖显式化比例；阻塞项数量 |
| 设置质量门 | 为每阶段定义“进入下一阶段前必须满足什么” | 质量门清单 / 验收标准 / 验证矩阵 | 本阶段如何证明“通过”？失败时是否能尽早发现？ | 只有主观 review；没有阈值；晚发现、贵返工 | 一次通过率；验证覆盖率；退回率 |
| 小步执行 | 先做最小可验证版本，快速暴露风险，再扩展范围 | 试点版本 / 实验记录 / 变更记录 | 最小可验证单元是什么？本轮要验证哪条假设？ | 一次做太大；没有实验设计；把试点结果当最终结论 | lead time；实验周期；小批量变更比例 |
| 用指标监控 | 同时监控结果、质量、速度、稳定性和风险，不只看“做完没” | KPI 看板 / SLO / 风险看板 | 哪些指标代表用户体验？哪些代表交付效率？哪些代表风险？ | 只看产出数量；忽略稳定性；没有预警阈值 | SLO 达成率；变更失败率；恢复时间；缺陷逃逸率 |
| 复盘并沉淀规则 | 把失败写成事实、根因、触发器和预防动作，并更新模板、检查单、测试集、规则库 | 复盘文档 / 新规则 / 更新后的 checklist | 这次失败是偶发疏忽，还是系统没有防呆？ | 只修个案；归因到个人；没有形成规则或验证 | 复盘完成率；规则更新数；重复问题复发率 |

## 检查清单与示例验收标准

| 步骤 | 典型 checklist | 示例验收标准 |
|---|---|---|
| 定义目标状态 | 是否写清 B 的结果状态；是否写清 owner；是否写清完成日期；是否写清成功与失败条件；是否区分“目标”和“手段” | `B` 可以被一段话准确重述；存在唯一 owner；存在明确截止时间；存在 3-5 条成功标准 |
| 发现真实问题 | 是否列出证据来源；是否区分症状与根因；是否写清受影响对象；是否定义“不解决会怎样”；是否记录假设 | 至少有 3 类证据；至少列出 3 条假设；问题表述可被利益相关方复述且无重大歧义 |
| 写清需求与约束 | 每条需求是否唯一编号；是否一条一义；是否避免“等等/适当/尽可能”等模糊词；是否标出约束、不做项、风险 | 100% 需求有唯一编号；100% 需求能对应验证方法；高风险项有 owner 与缓解动作 |
| 拆阶段与接口 | 是否写清输入/输出；是否定义阶段边界；是否标出依赖与阻塞；是否指定责任人；是否有交接格式 | 每阶段均有输入/输出/owner；关键依赖已显式化；接口项无“口头约定” |
| 设置质量门 | 是否给出通过阈值；是否说明验证方式；是否说明失败后回退或补救方式；是否尽量前置发现问题 | 每个 Gate 至少 1 个硬性阈值；100% Gate 有验证人；不通过时有明确处理路径 |
| 小步执行 | 是否控制变更批量；是否先验证最高风险假设；是否记录实验版本与结果；是否避免一次性大爆发 | 本轮范围可在一个周期内闭环；每轮只验证少量关键假设；所有实验有记录与结论 |
| 用指标监控 | 是否同时看速度、质量、稳定性、风险；是否设预警阈值；是否固定更新频率；是否有单一事实来源 | KPI 看板按固定频率更新；关键指标均有 owner；预警触发后有动作规则 |
| 复盘并沉淀规则 | 是否记录时间线；是否区分触发器与根因；是否有预防动作；是否转化为流程/模板/测试/监控更新；是否验证规则有效 | 复盘在约定时限内完成；至少 1 条系统性改进动作落地；相同问题复发率下降 |

## 进展指标与 KPI 表

KPI 不应只看“做了多少”，还要同时看“是否稳定、是否返工、是否在风险边界内推进”。下表是通用骨架，阈值是示例值，落地时按项目校准。

| KPI | 含义 | 建议公式 | 更新频率 | 示例阈值 | 主要用途 |
|---|---|---|---|---|---|
| 目标达成率 | 里程碑是否按计划兑现 | 已达成里程碑 / 计划里程碑 | 周 | >= 90% | 看结果推进 |
| Lead Time | 从“开始可执行”到“可验收”所需时间 | 验收时间 - 开始时间 | 周 | 持续下降 | 看推进效率 |
| 一次通过率 | 阶段是否常常一遍过 | 一次通过项 / 总提交项 | 周 | >= 80% | 看质量门是否有效 |
| 返工率 | 已完成项中被打回重做的比例 | 返工项 / 完成项 | 周 | <= 20% | 看需求/质量定义是否清楚 |
| 需求可追踪率 | 需求是否能追到验证与产出 | 有追踪链路需求 / 总需求 | 周 | 100% | 看系统性与 V&V 完整度 |
| 验证覆盖率 | 关键需求是否均有验证方法 | 有验证方法需求 / 关键需求 | 周 | 100% | 防止“无法验收” |
| 变更失败率 | 变更是否引入严重问题 | 失败变更 / 总变更 | 周 | 趋势下降 | 看稳定性 |
| 恢复时间 | 出问题后恢复到可接受状态需要多久 | 恢复完成时间 - 事件开始时间 | 周/月 | 趋势下降 | 看韧性 |
| SLO 达成率 | 关键服务/体验指标是否达成目标 | 达标周期数 / 总周期数 | 日/周 | 按项目定义 | 看用户感知质量 |
| 缺陷逃逸率 | 问题是否逃到后段或线上 | 后段发现缺陷 / 总缺陷 | 周/月 | 趋势下降 | 看前置质量控制 |
| 规则复用率 | 新项目是否复用已有规则与模板 | 复用规则数 / 可复用规则总数 | 月 | 趋势上升 | 看组织学习 |
| 复发问题率 | 同类问题是否重复出现 | 重复问题数 / 总问题数 | 月 | 趋势下降 | 看复盘是否有效 |

## 复盘与规则回流

复盘目标不是找人背锅，而是把事件记录清楚、理解贡献根因，并落实能降低复发概率或影响的预防动作。标准化复盘模板能让后续趋势分析更容易发现系统性问题。

最短回流流程：

```mermaid
flowchart LR
    A[记录事实] --> B[识别触发器与根因]
    B --> C[判断是哪一层失守]
    C --> D[生成系统性动作]
    D --> E[更新规则并验证]
```

一句话版本：

```text
先记事实，再找根因；先修当下，再补系统；凡是重复犯的错，都必须变成模板、检查单、测试、监控或规则。
```

## 失败转规则判断法

| 如果失败表现为 | 优先更新什么 |
|---|---|
| 目标模糊、团队理解不一致 | Brief 模板、成功定义模板 |
| 需求含糊、边界漏项 | 需求模板、需求检查单 |
| 交接频繁丢信息 | 阶段输出模板、接口表、RACI |
| 总是在后期才发现问题 | 质量门阈值、前移验证动作 |
| 改动一多就不稳 | 小批量发布策略、变更审批规则、SLO/预警 |
| 同类问题反复发生 | 标准复盘模板、复发检测、强制规则更新 |

## 记忆卡片

```text
从 A 到 B，不要只问“怎么做”。
先问：
1. B 到底是什么结果？
2. 真问题是什么？
3. 成功如何被验证？
4. 过程如何拆解？
5. 每一步的质量门是什么？
6. 现在先验证哪条最高风险假设？
7. 我用什么指标同时看速度、质量、稳定性？
8. 这次失败会沉淀成什么规则？
```
