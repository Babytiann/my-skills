一、Review 阶段
1. 这是一份实习生出的方案，你来 review 一下看看有没有什么设计缺陷、过度设计等等，给出中肯的修复建议，我们现在是内部开发阶段，没有真实用户，任何不是最佳实践的代码实现和架构设计，都会对后面造成巨大影响。不要考虑兼容现有设计，尽可能往最佳实践靠齐，只要不过度设计，允许抽出公共部分和重构等；但不要提前过度防御，太过 corner case 反倒是后续架构优化的负担

2. 把最终方案沉淀成一份 spec 文档：要改什么、为什么改、边界在哪，确保任何用户在拿到这篇文档之后就能立马上手，不要变更叙事

3. 自包含无需读原文档，逻辑清晰，语言流畅，换位思考同事没读代码也能理解，不要变更叙事（原方案 XX 后被否定，二稿改为...），直接描述正确方案，关键部分贴代码片段帮助理解，不要给代码定位

4. 现在拆阶段和 commits，我们预期会按照 XXX 方案来起 workflow，你先划分一下，我认可之后，再出一份新的执行计划，新的执行计划不引用 pr1 的，自包含。我们最后整体提交一个 PR；、开发阶段不要超过 4 个 stage，commit 不限制，尽量拆到 300k context 能执行完，review workflow 一个，是 review 那一套 * 2 轮（前面开发阶段是 1 轮），在开跑 workflow 后我就离开了，你自行监控和把控状况。在所有都完成之后，注意要给每个 agent 强调：我们现在是内部开发阶段，没有真实用户，任何不是最佳实践的代码实现和架构设计，都会对后面造成巨大影响。不要考虑兼容现有设计，尽可能往最佳实践靠齐，只要不过度设计，允许抽出公共部分和重构等；但不要提前过度防御，太过 corner case 反倒是后续架构优化的负担

5. review（用于 PR / 代码 review 的提示词）：

    在开始 review 之前，我们先讲讲我们产品一些基础的思想：
    1. 会做 remote：一个 daemon ＋ N 个配对设备，移动链路
    2. 所有窗口 / 设备背后是同一个人，不需要加入过重的版本控制
    3. 调用方不只是人：agent 经 buffin CLI 操作队列
    我们现在是内部开发阶段，没有真实用户，任何不是最佳实践的代码实现和架构设计，都会对后面造成巨大影响。不要考虑兼容现有设计，尽可能往最佳实践靠齐，只要不过度设计，允许抽出公共部分和重构等；但不要提前过度防御，太过 corner case 反倒是后续架构优化的负担
    你可以通过 /dispatch 让 codex 进行实机 e2e，并搭配提示词“我们现在是内部开发阶段，没有真实用户，任何不是最佳实践的代码实现和架构设计，都会对后面造成巨大影响。不要考虑兼容现有设计，尽可能往最佳实践靠齐，只要不过度设计，允许抽出公共部分和重构等；但不要提前过度防御，太过 corner case 反倒是后续架构优化的负担“，模型使用 gpt-6.1-Sol, xhigh, fullaccess
    注意检查基础设施，判断是否为最佳实践，我们不推荐重复造轮子，若有复用则复用最佳
    同时检查本次 PR 里所有注释，是否引用了外部文档、外部项目等本开源仓之外的东西，确保所有注释和代码逻辑一致且是自包含的
    检查代码逻辑，整体的数据流动是不是跟预期的一样，代码是否存在重复造轮子、低扩展性（如每新增部分都需要在每处都增加 if 判断逻辑），是否存在可以抽离作为公共附件的部分
    原则上不在消费方枚举 kind、再按 kind 分支决定行为，最好能力随 kind 声明，实现了某个接口就支持，没实现就是不支持，做到新增一种 owner 只需注册一次，资源模块和它的消费方都不改
