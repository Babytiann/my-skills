一、Review 阶段
1. 这是一份实习生出的方案，你来 review 一下看看有没有什么设计缺陷、过度设计等等，给出中肯的修复建议，我们现在是内部开发阶段，没有真实用户，任何不是最佳实践的代码实现和架构设计，都会对后面造成巨大影响。不要考虑兼容现有设计，尽可能往最佳实践靠齐，只要不过度设计，允许抽出公共部分和重构等；但不要提前过度防御，太过 corner case 反倒是后续架构优化的负担

2. 把最终方案沉淀成一份 spec 文档：要改什么、为什么改、边界在哪，确保任何用户在拿到这篇文档之后就能立马上手，不要变更叙事

3. 自包含无需读原文档，逻辑清晰，语言流畅，换位思考同事没读代码也能理解，不要变更叙事（原方案 XX 后被否定，二稿改为...），直接描述正确方案，关键部分贴代码片段帮助理解，不要给代码定位

4. 现在拆阶段和 commits，我们预期会按照 XXX 方案来起 workflow，你先划分一下，我认可之后，再出一份新的执行计划，新的执行计划不引用 pr1 的，自包含。我们最后整体提交一个 PR；、开发阶段不要超过 4 个 stage，commit 不限制，尽量拆到 300k context 能执行完，review workflow 一个，是 review 那一套 * 2 轮（前面开发阶段是 1 轮），在开跑 workflow 后我就离开了，你自行监控和把控状况。在所有都完成之后，注意要给每个 agent 强调：我们现在是内部开发阶段，没有真实用户，任何不是最佳实践的代码实现和架构设计，都会对后面造成巨大影响。不要考虑兼容现有设计，尽可能往最佳实践靠齐，只要不过度设计，允许抽出公共部分和重构等；但不要提前过度防御，太过 corner case 反倒是后续架构优化的负担
